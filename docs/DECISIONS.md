## 为什么用 Electron 而不是 Tauri

**背景**：目标是一个常驻托盘、按全局快捷键唤起的 launcher。这类应用最关心的三件事
是常驻内存、跨平台能力、发行链路。

**决策**：Electron + Vite + React。

**理由**：决定性因素是 **Linux 的 Wayland 全局快捷键**。

Wayland 的安全模型不允许应用自己注册全局快捷键，只能通过
XDG Desktop Portal (`org.freedesktop.portal.GlobalShortcuts`) 向合成器申请。
目前的情况：

- `tauri-apps/global-hotkey` 至今不支持这条路径（issue #28 从 2022 年挂到现在）
- Electron 已完成，Chromium / Electron 在 GlobalShortcuts 迁移 tracker 里被标为 done

虽然 v0.1 暂时只发 Windows，但这个决定让未来的 Linux 支持从"重写"变成"加一个模块"。

次要理由：electron-builder 的 NSIS / dmg / AppImage / deb 打包和签名流程是社区里
最成熟的一套，对一个要发 release 的开源项目来说，发行链路的确定性比内存更重要。

**代价**：常驻内存比 Tauri 多约 70MB。对一个 7×24 常驻的进程来说这是笔明账，
如果哪天内存变成第一约束，这里就该重新评估。

## 为什么不接管已打开的终端

**背景**：用户自然会期待"我看到列表里有个终端还开着，点一下就切回去"。

**决策**：只记录"打开过什么"，不读取、不接管、不复用已开的终端会话。

**理由**：终端窗口是**系统**开的，不是 TermHop 开的。系统和那个进程之间有一条
用于传输输入输出的通道（pty，Windows 上叫 ConPTY），而这条通道只有创建它的进程
握在手里。TermHop 用 `Process` 拉起终端时，这条通道归系统和 conhost / Windows
Terminal 所有，所以 TermHop 既读不到里面的内容，也没法往里面敲命令。

能做到"接管"只有一条路：自己创建 pty、自己管生命周期、自己渲染。那意味着要实现
ANSI 转义解析、颜色、光标移动、滚动回滚、崩溃恢复——也就是在写一个终端模拟器。

**代价**：用户少了一个看起来很酷的功能。缓解方式是接受它的替代价值：真正让人烦的
是"又要选一次 shell、又要输那条 cd"，而这部分完整解决了。

**相关**：[docs/DECISIONS.md 的开放问题](#开放问题分组这个字段到底该不该留) 里的
`wt -w` 命名窗口映射，是一条不用碰 pty 就能拿到部分会话感的折中路线。

## Windows 上怎么把终端拉起来

**背景**：`Process.start('pwsh.exe', ...)` 在 Windows 上有两个坑。

**决策**：

1. **控制台程序走 `cmd /c start`**，GUI 程序直接 spawn
2. **PowerShell 的启动脚本用 `-EncodedCommand`（base64 UTF-16LE）**

**理由**：

**为什么必须 `cmd /c start`**：用 detached 启动的控制台程序拿不到控制台窗口
（`DETACHED_PROCESS` 语义），进程会跑起来但完全不可见。`start` 会为目标创建新控制台。
Windows Terminal 是 GUI 程序，直接 spawn 即可，顺便让 cmd 的解析器离参数远一点。

**为什么要 base64**：路径里可能有空格、`[ ]`、单引号。`cmd /k "cd /d "C:\a b""` 这种
嵌套引号是经典陷阱。base64 里没有任何需要转义的字符，整条命令从此与引号无关。
`-LiteralPath` 则是为了让带 `[]` 的路径不被当成通配符。

`start` 的第一个带引号的参数会被当作窗口标题，所以路径前必须有空标题 `""`——
`"C:\Program Files\PowerShell\7\pwsh.exe"` 这种带空格的路径少了它会被吃掉。

**代价**：代码里多了一层 `cmd.exe` 转发。`verify-spawn.mjs` 里专门有断言守着这几条，
因为肉眼完全看不出来。

## 为什么 cmd 不支持启动命令

**背景**：`termhop add` 之外，允许给每个目录配一句 `npm run dev` 是很自然的需求。

**决策**：PowerShell 和 Windows Terminal 支持，Command Prompt 不支持。

**理由**：`cmd /k` 的参数解析没法可靠地把 `cd /d <路径> && <命令>` 整块传进去。
`&&` 会被外层 cmd 当成自己的命令分隔符执行，而不是传给新窗口——结果是**看起来成功了，
但新窗口里什么都没跑**。这种静默失败比直接报错更糟，所以宁可不给这个选项。

**代价**：用 cmd 的用户配不了启动命令。这是可发现的——设置页有说明。

## 为什么只做 Windows

**背景**：这个工具的痛点在任何平台都存在。

**决策**：v0.1 只发 Windows，macOS 和 Linux 的 spawn 层不写也不测。

**理由**：spawn 层是唯一真正平台相关的部分，UI 层和配置层是跨平台的。集中精力先把
最容易出错的一块做扎实，比三个平台都做到六十分有价值。

**代价**：Linux 用户暂时用不上。README 里明确写了，不藏着。

## 配置为什么是纯 JSON 而不是 SQLite

**背景**：这是个配置驱动的应用，数据量是"几十个目录"这个量级。

**决策**：单个 `config.json`，写入用「先写临时文件再 rename」。

**理由**：

- 可以被用户手改，也可以软链到 dotfiles 仓库用 git 管——这在开源工具里是真实需求
- 可以直接 diff
- 几十条记录不需要数据库

**代价**：没有并发写保护。这里的应对是"main 进程持有唯一缓存"，
CLI 通过单实例锁把写操作中继给运行中的实例，而不是自己直接改文件。

写入用 write-then-rename，这样进程崩溃不会截断配置。读的时候如果 JSON 坏了，
会把坏文件改名成 `config.json.broken-<时间戳>` 再用默认值启动，不让应用起不来。

## 开放问题：分组这个字段到底该不该留

**背景**：v0.1 有"分组"，用来把目录归类。三个使用下来，这个设计可能有过度。

**决策**：**暂不改**。先记在这里，等有真实用户反馈再动。

**质疑它的理由**：

1. **路径本身就是分组。** 如果布局是 `C:\work\a`、`C:\work\b`、`C:\oss\c`，
   分类信息已经编码在路径里了，让用户再录一遍是纯冗余。
2. **搜索已经解决了它。** 分组针对的是"目录太多认不清"，但认不清的时候搜两个字就行。
   分组要求你在**受益之前**就知道组名，这违反直觉。
3. **它是最先崩掉的字段。** 项目会增减、分组会过时，配置慢慢和现实脱节，
   而用户看不见哪里脱节了。

**但另一种分组是有价值的**：**会话归属**——这个目录属于哪个终端窗口。
它没有维护负担（一个下拉框，不用命名），而且是 `wt -w <组名>` 命名窗口映射的前提。

**所以可能的演进**：`group` 改名并降级成一个"归属终端窗口"的下拉框，
组织性分类交给路径和搜索，而不是维护一棵分类树。

**这个决策为什么还没做**：它是 schema 迁移，会动用户已有的数据。
在 P0（快速添加、回收站）验证完采纳情况之前，不该顺手改。

## 开机自启：为什么不能用 `openAtLogin` 判断状态

**背景**：设置页要显示"开机自动启动"当前是开还是关。

**决策**：用 `app.getLoginItemSettings().executableWillLaunchAtLogin` 加上
`launchItems` 匹配当前 exe，**不信任 `openAtLogin`**。

**理由**：Windows 上 `openAtLogin` 是**读回来不可信的**。探针实测：

```
setLoginItemSettings({ openAtLogin: true, ... })   -> 返回 undefined
getLoginItemSettings().openAtLogin                 -> false   ← 设了 true 却读出 false
getLoginItemSettings().executableWillLaunchAtLogin -> true    ← 这个才是对的
```

如果直接信 `openAtLogin`，设置页的勾会**永远显示为未勾**，哪怕系统里其实注册好了。

第二个坑：Electron 把注册项命名为 **`electron.app.<应用名>`**，不是产品名。所以
`TermHop` 写进注册表的键是 `electron.app.TermHop`。写验证脚本时按产品名去查会
误判成"功能没生效"。

**代价**：多了一个探针才能发现的隐式依赖。`verify-autostart.mjs` 现在直接查注册表，
覆盖"全新不注册 / 打开后注册且带 `--autostart` / 关闭后消失"三条，并且**只碰
`electron.app.TermHop` 这一个值，跑前快照、跑完还原**。

## 开机自启时为什么不弹窗

**背景**：开机自启时如果全局快捷键被别的软件抢走了，原本的逻辑会弹一个模态对话框。

**决策**：注册自启时带上 `--autostart` 参数，自启启动时抢不到快捷键只写日志，不弹窗。

**理由**：模态框会在**每一次登录时**弹出来，这比快捷键失灵本身糟糕得多。
开机场景下"安静"是硬要求，出了问题用户去设置里能看到。

**代价**：用户可能不知道快捷键没生效，托盘里也没有提示。

## 图标为什么是手写 PNG

**背景**：需要应用图标和托盘图标。

**决策**：`scripts/gen-icon.mjs` 用 `node:zlib` 手写 PNG 编码器，
形状用有符号距离场定义，3×3 超采样抗锯齿。

**理由**：不想为一个图标引入 `sharp` 或 `canvas` 这类原生依赖（安装脚本容易出问题，
还增加供应链面）。SDF 方案顺带保证了 32px 托盘图标和 256px 应用图标来自同一份定义。

**代价**：想改图标得改几何代码，不会用设计工具。不过对"一个箭头"来说够用了。
