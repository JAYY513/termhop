# 技术决策记录

这份文档解释"为什么是这样"，面向想改代码、想知道取舍的人。
想了解怎么用，看 [README](../README.md)。

每条记录包含：背景 / 决策 / 理由 / 代价。

## 为什么用 Electron 而不是 Tauri

**背景**：目标是一个常驻托盘、按全局快捷键唤起的 launcher。这类应用最关心的三件事
是常驻内存、跨平台能力、发行链路。

**决策**：Electron + Vite + React。

**理由**：决定性因素是 **Linux 的 Wayland 全局快捷键**。

Wayland 的安全模型不允许应用自己注册全局快捷键，只能通过
XDG Desktop Portal (`org.freedesktop.portal.GlobalShortcuts`) 向合成器申请。
目前的情况：

- `tauri-apps/global-hotkey` 至今不支持这条路径（issue #28 从 2022 年挂到现在）
- Electron 已完成，Chromium / Electron 在 GlobalShortcuts 迁移 tracker 里被标为 done

虽然 v0.1 暂时只发 Windows，但这个决定让未来的 Linux 支持从"重写"变成"加一个模块"。

次要理由：electron-builder 的 NSIS / dmg / AppImage / deb 打包和签名流程是社区里
最成熟的一套，对一个要发 release 的开源项目来说，发行链路的确定性比内存更重要。

**代价**：常驻内存比 Tauri 多约 70MB。对一个 7×24 常驻的进程来说这是笔明账，
如果哪天内存变成第一约束，这里就该重新评估。

## 为什么不接管已打开的终端

**背景**：用户自然会期待"我看到列表里有个终端还开着，点一下就切回去"。

**决策**：只记录"打开过什么"，不读取、不接管、不复用已开的终端会话。

**理由**：终端窗口是**系统**开的，不是 TermHop 开的。系统和那个进程之间有一条
用于传输输入输出的通道（pty，Windows 上叫 ConPTY），而这条通道只有创建它的进程
握在手里。TermHop 用 `Process` 拉起终端时，这条通道归系统和 conhost / Windows
Terminal 所有，所以 TermHop 既读不到里面的内容，也没法往里面敲命令。

能做到"接管"只有一条路：自己创建 pty、自己管生命周期、自己渲染。那意味着要实现
ANSI 转义解析、颜色、光标移动、滚动回滚、崩溃恢复——也就是在写一个终端模拟器。

**代价**：用户少了一个看起来很酷的功能。缓解方式是接受它的替代价值：真正让人烦的
是"又要选一次 shell、又要输那条 cd"，而这部分完整解决了。

**相关**：[docs/DECISIONS.md 的开放问题](#开放问题分组这个字段到底该不该留) 里的
`wt -w` 命名窗口映射，是一条不用碰 pty 就能拿到部分会话感的折中路线。

## Windows 上怎么把终端拉起来

**背景**：`Process.start('pwsh.exe', ...)` 在 Windows 上有两个坑。

**决策**：

1. **控制台程序走 `cmd /c start`**，GUI 程序直接 spawn
2. **PowerShell 的启动脚本用 `-EncodedCommand`（base64 UTF-16LE）**

**理由**：

**为什么必须 `cmd /c start`**：用 detached 启动的控制台程序拿不到控制台窗口
（`DETACHED_PROCESS` 语义），进程会跑起来但完全不可见。`start` 会为目标创建新控制台。
Windows Terminal 是 GUI 程序，直接 spawn 即可，顺便让 cmd 的解析器离参数远一点。

**为什么要 base64**：路径里可能有空格、`[ ]`、单引号。`cmd /k "cd /d "C:\a b""` 这种
嵌套引号是经典陷阱。base64 里没有任何需要转义的字符，整条命令从此与引号无关。
`-LiteralPath` 则是为了让带 `[]` 的路径不被当成通配符。

`start` 的第一个带引号的参数会被当作窗口标题，所以路径前必须有空标题 `""`——
`"C:\Program Files\PowerShell\7\pwsh.exe"` 这种带空格的路径少了它会被吃掉。

**代价**：代码里多了一层 `cmd.exe` 转发。`verify-spawn.mjs` 里专门有断言守着这几条，
因为肉眼完全看不出来。

## 为什么 cmd 不支持启动命令

**背景**：`termhop add` 之外，允许给每个目录配一句 `npm run dev` 是很自然的需求。

**决策**：PowerShell 和 Windows Terminal 支持，Command Prompt 不支持。

**理由**：`cmd /k` 的参数解析没法可靠地把 `cd /d <路径> && <命令>` 整块传进去。
`&&` 会被外层 cmd 当成自己的命令分隔符执行，而不是传给新窗口——结果是**看起来成功了，
但新窗口里什么都没跑**。这种静默失败比直接报错更糟，所以宁可不给这个选项。

**代价**：用 cmd 的用户配不了启动命令。这是可发现的——设置页有说明。

## 为什么只做 Windows

**背景**：这个工具的痛点在任何平台都存在。

**决策**：v0.1 只发 Windows，macOS 和 Linux 的 spawn 层不写也不测。

**理由**：spawn 层是唯一真正平台相关的部分，UI 层和配置层是跨平台的。集中精力先把
最容易出错的一块做扎实，比三个平台都做到六十分有价值。

**代价**：Linux 用户暂时用不上。README 里明确写了，不藏着。

## 配置为什么是纯 JSON 而不是 SQLite

**背景**：这是个配置驱动的应用，数据量是"几十个目录"这个量级。

**决策**：单个 `config.json`，写入用「先写临时文件再 rename」。

**理由**：

- 可以被用户手改，也可以软链到 dotfiles 仓库用 git 管——这在开源工具里是真实需求
- 可以直接 diff
- 几十条记录不需要数据库

**代价**：没有并发写保护。这里的应对是"main 进程持有唯一缓存"，
CLI 通过单实例锁把写操作中继给运行中的实例，而不是自己直接改文件。

写入用 write-then-rename，这样进程崩溃不会截断配置。读的时候如果 JSON 坏了，
会把坏文件改名成 `config.json.broken-<时间戳>` 再用默认值启动，不让应用起不来。

## 开放问题：分组这个字段到底该不该留

**背景**：v0.1 有"分组"，用来把目录归类。三个使用下来，这个设计可能有过度。

**决策**：**暂不改**。先记在这里，等有真实用户反馈再动。

**质疑它的理由**：

1. **路径本身就是分组。** 如果布局是 `C:\work\a`、`C:\work\b`、`C:\oss\c`，
   分类信息已经编码在路径里了，让用户再录一遍是纯冗余。
2. **搜索已经解决了它。** 分组针对的是"目录太多认不清"，但认不清的时候搜两个字就行。
   分组要求你在**受益之前**就知道组名，这违反直觉。
3. **它是最先崩掉的字段。** 项目会增减、分组会过时，配置慢慢和现实脱节，
   而用户看不见哪里脱节了。

**但另一种分组是有价值的**：**会话归属**——这个目录属于哪个终端窗口。
它没有维护负担（一个下拉框，不用命名），而且是 `wt -w <组名>` 命名窗口映射的前提。

**所以可能的演进**：`group` 改名并降级成一个"归属终端窗口"的下拉框，
组织性分类交给路径和搜索，而不是维护一棵分类树。

**这个决策为什么还没做**：它是 schema 迁移，会动用户已有的数据。
在 P0（快速添加、回收站）验证完采纳情况之前，不该顺手改。
（回收站和快速添加都已落地，见下面的「快速添加为什么是面板里的一行」。）

## 快速添加：为什么是面板里的一行，不是设置里的表单

**背景**：`Ctrl+N` 原本的实现是「把设置窗口叫起来，在那边打开一个空白表单」。
README 写的是「启动器里一步到位」，但代码做的不是这件事。

**决策**：在路径输入框下面加一条合成行「存为常用目录」，
`↓` 一下回车就存，全程不离开面板。`Ctrl+N` 改成保存当前输入的目录；
输入框为空时才退回打开设置表单。

**理由**：面板里那个路径是用户刚亲手敲进去的，跳到设置窗口就等于把它扔掉重敲一遍。
而这个窗口只有 300px 宽、贴在光标上，另一个窗口可能在几百像素外、还可能压在别的窗口底下——
为一个"存一下"付出的注意力成本，和它省下来的完全不成比例。

**为什么不是弹出一个小表单**：为了存一个目录要填的东西本来就能事后在设置里改，
而"填表"这件事本身就是打断。合成行的做法是**只做唯一合理的默认值**
（标题留空回落到文件夹名、分组留空、shell 用面板本来就会用的那个），
需要更细再自己去设置页。

**为什么保存之后不顺手把终端也开了**：一次按键同时写配置和拉进程，
"到底打开没打开"就没法回答了。Launcher 的 `Phase` 联合类型存在的全部理由
就是不让"成功""进行中""失败"长得一样，所以这里不能开这个口子。
实际流程是：保存 → 合成行变成真实行、搜索框换成目录名、状态栏显示「已保存 · 回车打开」
→ 再回车开终端。列表可见地变化本身就是最清楚的反馈。

**代价**：存下来的条目没有标题、没分组、没启动命令，要改得去设置页。
这比"存的时候问四个问题"快，代价是想不起来刚才存的东西带不带启动命令——
真发生了再去设置里看一眼就行。

## Ctrl+N 为什么是「添加」，而 Ctrl+P 只剩「向上」

**背景**：`Ctrl+N` 从**第一个 commit 起就是死代码**。keydown 处理器里先命中的是导航分支
（`Ctrl+N` 被当成「往上一项」），它 `return` 之后，底下的「添加」分支永远轮不到。
于是 footer 一直写着「Ctrl+N 添加」、设置页一直写着「或按 Ctrl+N 从启动器直接添加」，
而实际按下去是**选中行往上挪一格**。

同一个键还在 README 的快捷键表里被写了**两遍**：一行说 `Ctrl`+`P` `Ctrl`+`N` 上下移动一项，
另一行说 `Ctrl` + `N` 保存当前输入的目录。文档和实现互相矛盾，三方各说各话。

**决策**：`Ctrl+N` 归「添加」——footer、设置页和「快速添加为什么是面板里的一行」
那一条决策都是这么写的，它是这个功能对外的契约。导航别名里的 `Ctrl+N` 去掉，
`Ctrl+P` 保留，并且**改成向上**：P 是 previous，向上是它在别处（Emacs、less、
readline）唯一的意思。向下继续用 `↓`。

**理由**：一个键只能有一个意思，而且要选**被写进界面的那个**，不是被写进实现的那个。
`Ctrl+P` 原本是向下、`Ctrl+N` 原本是向上，两个都和字面相反——那对别名不是"有个约定"，
是照着抄反了。与其保留一对反着的别名，不如留一个方向正确的。

**被否决的方案**：

- **把「添加」挪到别的键（比如 `Ctrl+S`）**：footer、设置页、README、DECISIONS 四处
  都要跟着改，用户刚记住的键就废了。`Ctrl+N` 的契约写在界面上，改它比修它贵。
- **保留 `Ctrl+P` 向下、`Ctrl+N` 向上这一对**：那等于导航的「向下」留着、「向上」没了，
  剩一个方向不全的别名；而且 P 向下读起来是反的。
- **去掉所有 Ctrl 导航别名**：`↑` `↓`、`PageUp`/`PageDown`、`Home`/`End`、`1`–`9`
  已经覆盖了移动，一个别名都不留也很干净。但那是删功能，比修 bug 贵。

**代价**：`Ctrl+↓` 这个组合没有了，往下走只能用 `↓`。

**怎么保证它不再退化**：快捷键这一层之前**没有任何自动化测试**——`verify:window`
只测主进程，渲染层一个用例都没有。新增 `npm run verify:shortcuts`：
用真实 Electron 键盘事件驱动**真实的 Launcher 组件**（只把 IPC 换成记录器，
不会真的拉起终端），逐条断言 footer 宣传的四个键各自做了什么，
并断言 README 的快捷键表和 footer 不打架。

## 目录存在性校验为什么下沉到 addEntryToConfig

**背景**：`termhop add .` 会先 `existsSync` 再调用 `addEntryToConfig`，
设置表单直接调用、不检查。

**决策**：校验放进 `addEntryToConfig` 本身，调用方不再自己查。

**理由**：不存在的目录被存进去，就是一条**永远打不开**的死条目——
之后每次按回车都报"目录不存在"，用户只能去设置里翻回收站才知道当初打错了什么。
一个只在部分调用方存在的校验，等于没有校验。

**代价**：`addEntryToConfig` 从纯函数变成了碰文件系统的函数。
它已经在同一个文件里做 `existsSync` 了，所以这个代价本来就付着。

## 新条目的默认 shell 为什么不再写死 powershell

**背景**：面板打开一个未保存路径时走 `pwsh → powershell → wt → cmd` 的顺序，
而 `addEntryToConfig` 默认写死 `'powershell'`。结果：用户用 `pwsh` 打开了一个目录，
把它存下来，之后再打开就变成了 Windows PowerShell，且没有任何提示。

**决策**：顺序只写一次，放在 `@shared/types` 的 `PREFERRED_SHELL_ORDER`，
主进程和渲染层共用。渲染层用它给"存为常用目录"那行显示 badge。

**理由**：那行右边的 badge 如果和实际存下来的 shell 不一致，
就是在骗人——比没有 badge 更糟。共用一份顺序是唯一的保证。

**代价**：新增 shell 要改共享常量而不是只改 `shells.ts`。
但改一处总比两处各改一次然后各自漂移要好。

## 换 shell 为什么是「一个选择器」而不是「循环到下一个」

**背景**：`Shift+Enter` 原本沿着写死的 `['pwsh','powershell','cmd','wt']`
按下就切到下一个并立刻打开。

**决策**：`Shift+Enter` 打开一个 shell 选择器——列表换成已安装的 shell，
`↑↓` 移动、`Enter` 确认、`1`–`4` 直选、`Esc` 返回。**什么都不打开**，直到确认。

**理由**：循环有两个毛病，加预览也治不好。

1. **按了没法撤销。** 每按一次都真的开一个终端，而 `entry:open` 成功后调
   `recordUse` 把 `lastShell` 推到刚开那个，循环位置就往前走。
   所以"按过头了退回去"不是撤销，是**再按一次、再开一个窗口**。
2. **循环是盲的一比特。** 四个取值你只能"往后挪一格"，没法表达"我要 wt"。
   而且原顺序里 `pwsh` 和 `powershell` 挨着，从 pwsh 切过去看起来什么都没变。

**中间走过的一步**：先在 footer 里加了「Shift+Enter 换到 cmd」这种预览，
并且把循环限制在已安装的 shell 里（原来会转进没装的，直接启动失败）。
预览确实去掉了"不知道会发生什么"，但另外两条——没法撤销、没法瞄准——原封不动。
所以选择器不是推翻预览，是补上预览补不了的那部分；footer 那条提示也随之
变成了「Shift+Enter 选shell」，因为它已经不再预告一个具体目标。

**为什么是替换列表而不是弹个面板**：面板只有 680px 宽、只有一个输入框，
第二个浮层没有地方放而不必挪动它正在为之选择的那份列表。
选择器打开时输入框变成 `readOnly` 并显示那一行的名字：焦点仍在输入框上
（按键是挂在 window 上的），但打字不会去过滤一个已经冻结的列表。

**代价**：多一步。想换 shell 从一次按键变成"进选择器 + 确认"两次。
换来的是可以指名要哪一个。

**相关**：`Alt+Enter` 在「在此路径打开终端」和「存为常用目录」这两行上
曾经什么都不做——`reveal` 这个 target 挂在 entryId 上，而一个没保存的路径
没有 entry。footer 明明写着「打开文件夹」。现在有了 `entry:revealPath`。

## 为什么启动器不做多列、不做视图切换

**背景**：目录多起来之后面板一次只显示 7–8 行（窗口高度封顶 470px），
于是有两条路看起来很自然：把列表排成多列，或者加一个"列表视图 / 网格视图"的切换。

**决策**：都不做。只把分组标题做成吸顶，另外补上 `PageUp`/`PageDown`/`Home`/`End`。

**理由**：

1. **"我到底存了哪些目录"已经被满足了，在设置页。** 「常用目录」列全部条目，
   带分组下拉、shell 下拉、每组数量和排序。启动器不需要再长出一个总览。
2. **多列和这个应用的核心约束正面冲突。** 宽度是钉死的 680px
   （`setMinimumSize` 和 `setMaximumSize` 都用它，`verify:window` 专门断言过），
   而整个应用是"窗口按内容自适应"的——renderer 报高度、主进程调
   `resizeLauncherToContent`。要放三四列就得拉宽，一拉宽，搜索结果条数一变宽度就跳。
   面板小、不挡工作窗口，是它全部价值所在，拿这个换行数是亏的。
3. **多列解决的不是真问题。** 目录多的时候缺的不是"一次看见更多"，是"快速找到某一个"，
   而这件事搜索已经在两三个字符内做完了。多列只是把"翻五十次"换成"在七个格子里找"，
   而你本来就不该翻。
4. **它会变成一个模式。** 多列要重新定义 `←→`、二维滚动、选中态和序号怎么算。
   为一个不是主路径的场景加模式，和这个项目一贯的做法相反——分组那个开放问题的
   核心理由正是"要求你在受益之前就知道组名"。

**代价**：搜索框有内容时列表没有分组标题（`sections` 在有查询词时返回单一无名分组），
所以吸顶标题只在未筛选的浏览态下有意义。而未筛选浏览本身就是少数场景。

**相关**：`PageUp`/`PageDown` 的步长从 DOM 量出来（`pageStep()`），不是写死的——
自适应高度下列表可能是两行也可能是八行。`Home`/`End` 只在搜索框为空时接管，
有查询词时留给输入框的文本光标。

## 开机自启：为什么不能用 `openAtLogin` 判断状态

**背景**：设置页要显示"开机自动启动"当前是开还是关。

**决策**：用 `app.getLoginItemSettings().executableWillLaunchAtLogin` 加上
`launchItems` 匹配当前 exe，**不信任 `openAtLogin`**。

**理由**：Windows 上 `openAtLogin` 是**读回来不可信的**。探针实测：

```
setLoginItemSettings({ openAtLogin: true, ... })   -> 返回 undefined
getLoginItemSettings().openAtLogin                 -> false   ← 设了 true 却读出 false
getLoginItemSettings().executableWillLaunchAtLogin -> true    ← 这个才是对的
```

如果直接信 `openAtLogin`，设置页的勾会**永远显示为未勾**，哪怕系统里其实注册好了。

第二个坑：Electron 把注册项命名为 **`electron.app.<应用名>`**，不是产品名。所以
`TermHop` 写进注册表的键是 `electron.app.TermHop`。写验证脚本时按产品名去查会
误判成"功能没生效"。

**代价**：多了一个探针才能发现的隐式依赖。`verify-autostart.mjs` 现在直接查注册表，
覆盖"全新不注册 / 打开后注册且带 `--autostart` / 关闭后消失"三条，并且**只碰
`electron.app.TermHop` 这一个值，跑前快照、跑完还原**。

## 开机自启时为什么不弹窗

**背景**：开机自启时如果全局快捷键被别的软件抢走了，原本的逻辑会弹一个模态对话框。

**决策**：注册自启时带上 `--autostart` 参数，自启启动时抢不到快捷键只写日志，不弹窗。

**理由**：模态框会在**每一次登录时**弹出来，这比快捷键失灵本身糟糕得多。
开机场景下"安静"是硬要求，出了问题用户去设置里能看到。

**代价**：用户可能不知道快捷键没生效，托盘里也没有提示。

## 图标为什么是手写 PNG

**背景**：需要应用图标和托盘图标。

**决策**：`scripts/gen-icon.mjs` 用 `node:zlib` 手写 PNG 编码器，
形状用有符号距离场定义，3×3 超采样抗锯齿。

**理由**：不想为一个图标引入 `sharp` 或 `canvas` 这类原生依赖（安装脚本容易出问题，
还增加供应链面）。SDF 方案顺带保证了 32px 托盘图标和 256px 应用图标来自同一份定义。

**代价**：想改图标得改几何代码，不会用设计工具。不过对"一个箭头"来说够用了。
